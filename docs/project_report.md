## 1. Abstract

MorphGuard is an evolutionary real-time log analytics system designed to detect anomalies in cloud environments using streaming technologies and machine learning. The system implements a SIEM-inspired (Security Information and Event Management) architecture that combines log ingestion, behavioral anomaly detection, evolutionary optimization through Genetic Algorithms, and security alert generation. The name "MorphGuard" reflects the dual nature of the system: behavior that *morphs* — where models are continuously re-optimized by a genetic algorithm — in service of *guarding* the cloud estate against threats and anomalies.

The system processes HDFS (Hadoop Distributed File System) log data, extracting structured features from raw log entries and applying Isolation Forest models for unsupervised anomaly detection. A Genetic Algorithm (GA) is employed to optimize feature selection, hyperparameter tuning, and contamination thresholds, enabling the system to evolve its detection capabilities over time. The backend exposes a RESTful API secured with JWT-based authentication, supporting real-time analytics dashboards.

This report details the system architecture, implementation methodology, experimental results, and the novel application of evolutionary computation to continuously improve anomaly detection accuracy in cloud security monitoring.

## 2. Introduction

### 2.1 Background and Motivation

Cloud computing has fundamentally transformed how organizations deploy, manage, and scale their applications and infrastructure. As cloud environments grow in complexity, the volume of system logs generated by distributed services, virtual machines, containers, and orchestration platforms has exploded exponentially. According to industry estimates, a typical enterprise cloud deployment generates terabytes of log data daily, creating both an opportunity and a challenge for security teams.

Traditional security monitoring approaches rely heavily on predefined rules and signature-based detection systems. While effective against known threats, these approaches fundamentally fail at detecting novel attack patterns, zero-day exploits, and subtle behavioral anomalies that may indicate sophisticated intrusions or system degradation. The static nature of rule-based systems means they cannot adapt to the evolving threat landscape without manual intervention from security analysts.

The motivation for MorphGuard stems from the recognition that:

1. **Volume Exceeds Human Capacity**: The sheer volume of log data makes manual analysis impractical. Security analysts face alert fatigue from systems that generate thousands of alerts daily, most of which are false positives.

2. **Threats Evolve Faster Than Rules**: Adversaries continuously adapt their techniques, rendering static detection rules obsolete. A system that evolves its detection models can better keep pace with emerging threats.

3. **Behavioral Anomalies Require Context**: Many security incidents manifest not as single suspicious events but as subtle deviations from normal behavioral patterns. Detecting these requires statistical models that understand baseline behavior.

4. **Automation Is Essential**: The time between initial compromise and data exfiltration (dwell time) continues to shrink. Automated detection and alerting can significantly reduce response times compared to periodic manual log review.

### 2.2 Problem Statement

Design and implement a scalable, intelligent log analytics system capable of:

- Ingesting and parsing heterogeneous log formats from cloud environments at scale
- Extracting meaningful behavioral features from structured log data
- Training and deploying unsupervised anomaly detection models that do not require labeled training data for initial deployment
- Continuously optimizing detection models through evolutionary algorithms that improve accuracy metrics over successive generations
- Providing a secure, real-time API for analytics dashboards and alert consumption
- Managing model versioning and evolution to ensure only superior models are promoted to production

### 2.3 Objectives

The primary objectives of MorphGuard are as follows:

1. **Log Parsing and Ingestion**: Develop a modular parsing framework that supports multiple log formats (HDFS, Django, and extensible to additional formats) and extracts structured fields from raw log entries.

2. **Feature Engineering**: Design a comprehensive feature extraction pipeline that transforms raw structured log data into numerical features suitable for machine learning models, capturing temporal patterns, event distributions, and error characteristics.

3. **Anomaly Detection**: Implement unsupervised anomaly detection using Isolation Forest models that can identify anomalous behavior patterns without requiring pre-labeled training data.

4. **Evolutionary Optimization**: Apply Genetic Algorithms to simultaneously optimize feature selection and model hyperparameters, enabling the system to discover optimal configurations that maximize detection accuracy.

5. **Model Evolution**: Build a model versioning and promotion system that evaluates candidate models against the current production model and promotes only those that demonstrate measurable improvement.

6. **Secure API**: Expose a RESTful API with JWT-based authentication for integration with analytics dashboards and downstream security tools.

7. **Scalability**: Design the system architecture to handle large-scale log data (the target dataset contains ~1.5GB of raw HDFS logs with 575,000+ block IDs).

### 2.4 Scope

This project focuses on the backend analytics pipeline and does not include:

- A frontend dashboard (which exists as a separate companion repository)
- Real-time streaming ingestion (the current implementation processes batch data; streaming is an identified future enhancement)
- Multi-tenancy and enterprise deployment features
- Integration with specific cloud provider APIs (AWS CloudWatch, Azure Monitor, GCP Logging connectors are defined but not yet implemented)

The system uses the HDFS log dataset from a Hadoop cluster as the primary evaluation dataset, though the parser architecture supports extensibility to additional log formats.

## 3. Literature Review

### 3.1 Traditional Log Analysis Approaches

Log analysis has been a cornerstone of system administration and security monitoring since the earliest days of computing. Traditional approaches can be broadly categorized as follows:

**Rule-Based Systems**: These systems use predefined patterns, regular expressions, and conditional logic to identify known indicators of compromise (IOCs) or operational anomalies. Tools such as grep, awk, and sed have been the workhorses of ad-hoc log analysis for decades. More sophisticated systems like OSSEC and Snort extend this concept with curated rule databases maintained by security communities.

The primary limitation of rule-based systems is their reactive nature: a rule must be written for each new threat pattern, creating a perpetual gap between the emergence of new attack techniques and the creation of rules to detect them.

**Statistical Threshold-Based Monitoring**: Systems like Nagios and Zabbix use statistical thresholds (e.g., "alert if CPU usage exceeds 90% for 5 minutes") to detect operational anomalies. While effective for infrastructure monitoring, these approaches struggle with the complex, multi-dimensional patterns that characterize security incidents.

**Log Aggregation and Search**: The ELK Stack (Elasticsearch, Logstash, Kibana) and Splunk revolutionized log management by providing centralized collection, indexing, and search capabilities. These platforms excel at enabling human analysts to investigate incidents but still rely heavily on manual query construction and human expertise for detection.

### 3.2 Machine Learning for Anomaly Detection

The application of machine learning to anomaly detection in system logs has been an active area of research over the past decade.

**Supervised Approaches**: Methods such as Support Vector Machines (SVM), Random Forests, and deep learning classifiers have shown strong detection accuracy when sufficient labeled data is available. However, labeled security data is expensive to produce, difficult to maintain as systems evolve, and inherently biased toward known attack types.

**Unsupervised Approaches**: Techniques that do not require labeled data are particularly attractive for security applications:

- **Isolation Forest** (Liu et al., 2008): An ensemble method that isolates anomalies by randomly partitioning the feature space. Anomalous points, being few and different, require fewer random partitions to be isolated than normal points. This is the approach selected for MorphGuard due to its computational efficiency and strong performance on high-dimensional data.

- **Autoencoders**: Neural network architectures trained to reconstruct their input. Points with high reconstruction error are flagged as anomalous. While powerful, autoencoders require careful architecture design and are more computationally expensive than tree-based methods.

- **Clustering-Based Methods**: Algorithms like DBSCAN and k-means can identify anomalies as points that do not belong to any cluster or belong to small, sparse clusters. These methods struggle with high-dimensional data and require tuning of distance metrics and cluster parameters.

- **Principal Component Analysis (PCA)**: PCA-based anomaly detection projects data into a lower-dimensional space and flags points with high reconstruction residuals. While computationally efficient, PCA assumes linear relationships in the data.

**Deep Learning Approaches**: Recent work has applied LSTM networks, Transformer models, and attention mechanisms to log anomaly detection, treating log sequences as natural language. DeepLog (Du et al., 2017) and LogRobust (Zhang et al., 2019) represent notable examples. These approaches can capture complex temporal dependencies but require significant computational resources for training.

### 3.3 Evolutionary Algorithms in Security Systems

Evolutionary algorithms (EAs) have found applications across various security domains:

**Genetic Algorithms for Feature Selection**: Feature selection is critical in machine learning, as irrelevant features can degrade model performance and increase computational cost. GAs have been successfully applied to feature selection in intrusion detection systems, where the search space is too large for exhaustive evaluation.

**Hyperparameter Optimization**: Traditional hyperparameter tuning approaches (grid search, random search) scale poorly with the number of parameters. GAs offer a more efficient search strategy by maintaining a population of candidate solutions that evolve toward optimal configurations through selection, crossover, and mutation.

**Co-Evolutionary Approaches**: Some research has explored co-evolutionary systems where detection models and simulated attacks evolve simultaneously, creating an arms race that drives continuous improvement in both offensive and defensive capabilities.

**Genetic Programming for Rule Generation**: GP has been used to automatically generate detection rules from log data, combining the interpretability of rule-based systems with the adaptability of evolutionary computation.

### 3.4 Existing SIEM Systems

Security Information and Event Management (SIEM) systems represent the current state-of-the-art in enterprise security monitoring:

**Commercial SIEMs**: Products like Splunk Enterprise Security, IBM QRadar, Microsoft Sentinel, and Google Chronicle provide comprehensive log collection, correlation, alerting, and investigation capabilities. These systems increasingly incorporate machine learning for anomaly detection but typically treat their ML components as black boxes with limited customization.

**Open-Source SIEMs**: The ELK Stack with Security plugin, Wazuh, and OSSIM provide open-source alternatives with varying degrees of machine learning integration. While more customizable than commercial offerings, these systems still primarily rely on rule-based detection.

**Cloud-Native Security Tools**: AWS GuardDuty, Azure Defender, and GCP Security Command Center provide cloud-native detection capabilities but are inherently tied to their respective cloud ecosystems and offer limited transparency into their detection methodologies.

### 3.5 Research Gap

Despite the advances in both machine learning-based anomaly detection and evolutionary algorithms, there is a notable gap in systems that:

1. **Combine unsupervised detection with evolutionary optimization** in a single, integrated pipeline
2. **Continuously evolve detection models** without human intervention, adapting to changing system behavior
3. **Jointly optimize feature selection and model hyperparameters**, recognizing that the optimal feature subset is dependent on model configuration
4. **Provide transparent model versioning and evolution tracking**, enabling security teams to understand why models change and verify that changes improve detection quality

MorphGuard addresses this gap by implementing an end-to-end system that integrates log parsing, feature engineering, unsupervised anomaly detection, and genetic algorithm optimization into a cohesive pipeline with model evolution tracking.

## 4. System Architecture

### 4.1 High-Level Overview

MorphGuard follows a modular pipeline architecture where data flows through distinct processing stages:

```
Raw Logs --> Parser --> Feature Engineering --> Detection --> Optimization --> Alert System
                                                   ^                |
                                                   +-- Model Evolution --+
```

Each stage is implemented as an independent module with well-defined interfaces, enabling individual components to be tested, replaced, or scaled independently.


### 4.3 Data Flow Pipeline

The data processing pipeline consists of the following stages:

**Stage 1: Data Acquisition**
Raw HDFS log data (~1.5GB) and anomaly labels are retrieved from Hugging Face using the download_dataset.py script. The dataset is stored locally in data/raw/hdfs/.

**Stage 2: Log Parsing**
The HDFSParser processes raw log files, extracting structured fields from each log line using regular expression pattern matching. Each line is decomposed into timestamp, PID, log level, component, block ID, content, and event type.

**Stage 3: Feature Engineering**
The FeatureExtractor aggregates parsed log entries by block ID, computing numerical features that capture the behavioral profile of each block lifecycle including event count distributions, temporal features, error indicators, and information-theoretic measures.

**Stage 4: Model Training**
The Isolation Forest model is trained on the extracted features using unsupervised learning. The model learns the "normal" distribution of features and identifies blocks whose feature vectors deviate significantly from this baseline.

**Stage 5: Prediction and Evaluation**
The trained model generates anomaly predictions for each block, which are evaluated against ground-truth labels using accuracy, precision, recall, and F1 score.

**Stage 6: Evolutionary Optimization**
The Genetic Algorithm explores the joint space of feature subsets and hyperparameter configurations, evolving a population of candidate models across multiple generations.

**Stage 7: Model Evolution**
Optimized candidate models are compared against the current production model. Superior candidates are promoted to the next version, while inferior candidates are archived.

## 5. Design and Implementation

### 5.1 Log Parsing Module

The parsing module implements a plugin-based architecture where each log format is handled by a dedicated parser class that extends the abstract BaseParser.

#### 5.1.1 Base Parser Interface

The BaseParser class defines the contract that all parser implementations must fulfill:

```python
class BaseParser(ABC):
    @abstractmethod
    def parse(self, filepath: str) -> pd.DataFrame:
        """Parse a log file and return structured data as a DataFrame."""
        pass
```

This abstraction enables the system to support multiple log formats without modification to the downstream feature engineering and detection pipelines.

#### 5.1.2 HDFS Parser

The HDFSParser is the primary parser implementation, designed to process Hadoop Distributed File System logs. It uses a compiled regular expression pattern to extract structured fields from each log line.

**Log Line Format Example**:
```
081109 203518 148 INFO dfs.DataNode$PacketResponder: PacketResponder 1 for block blk_38865049064139660 terminating
```

**Extracted Fields**:

| Field       | Description                            | Example                        |
|-------------|----------------------------------------|--------------------------------|
| date        | Date in YYMMDD format                 | 081109                         |
| time        | Time in HHMMSS format                 | 203518                         |
| pid         | Process identifier                    | 148                            |
| level       | Log severity level                    | INFO                           |
| component   | Source component                      | dfs.DataNode$PacketResponder   |
| block_id    | HDFS block identifier                 | blk_38865049064139660          |
| content     | Full log message text                 | (original message)             |
| event_type  | Classified event category             | PACKET_RESPONDER               |

**Event Type Classification**: The parser classifies each log entry into predefined event types based on keyword matching in the content field. The following event types are recognized:

| Event Type              | Description                                           |
|------------------------|-------------------------------------------------------|
| RECEIVING_BLOCK        | Block reception initiated                             |
| RECEIVED_BLOCK         | Block reception completed                             |
| SERVING_BLOCK          | Block serving to a client                             |
| REPLICATION            | Block replication events                              |
| DELETION               | Block deletion events                                 |
| BLOCK_MAP              | Block map operations                                  |
| PACKET_RESPONDER       | Packet response events                                |
| WRITE_BLOCK            | Block write operations                                |
| ALLOCATE               | Block allocation events                               |
| VERIFICATION           | Block verification and checksum events                |
| STATE_CHANGE           | DataNode state change events                          |
| OTHER                  | Events not matching any known pattern                 |

#### 5.1.3 Django Parser

The DjangoParser implements parsing for Django web framework access logs. While not used in the primary detection pipeline, this parser demonstrates the system extensibility to web application log formats.

### 5.2 Feature Engineering Module

The feature engineering module transforms raw parsed log data into numerical feature vectors suitable for machine learning model input.

#### 5.2.1 Block-Level Aggregation

Since anomaly labels in the HDFS dataset are assigned at the block level, features must be aggregated from individual log entries to the block level. The FeatureExtractor performs this aggregation using pandas groupby operations on the block_id field.

#### 5.2.2 Feature Categories

The following feature categories are extracted for each block:

**Event Count Features**:

| Feature                    | Description                                            |
|---------------------------|--------------------------------------------------------|
| n_events                  | Total number of log entries for the block              |
| n_receiving_block         | Count of RECEIVING_BLOCK events                        |
| n_received_block          | Count of RECEIVED_BLOCK events                         |
| n_serving_block           | Count of SERVING_BLOCK events                          |
| n_replication             | Count of REPLICATION events                            |
| n_deletion                | Count of DELETION events                               |
| n_block_map               | Count of BLOCK_MAP events                              |
| n_packet_responder        | Count of PACKET_RESPONDER events                       |
| n_write_block             | Count of WRITE_BLOCK events                            |
| n_allocate                | Count of ALLOCATE events                               |
| n_verification            | Count of VERIFICATION events                           |
| n_state_change            | Count of STATE_CHANGE events                           |
| n_other                   | Count of unclassified events                           |

**Temporal Features**:

| Feature                    | Description                                            |
|---------------------------|--------------------------------------------------------|
| session_duration_seconds  | Time span from first to last event for the block       |
| mean_time_gap             | Average time between consecutive events                |
| std_time_gap              | Standard deviation of inter-event time gaps            |
| max_time_gap              | Maximum time gap between consecutive events            |

**Error and Severity Features**:

| Feature                    | Description                                            |
|---------------------------|--------------------------------------------------------|
| n_error                   | Count of ERROR-level log entries                       |
| n_warn                    | Count of WARN-level log entries                        |
| error_ratio               | Proportion of events at ERROR level                    |
| is_error                  | Binary indicator: 1 if any ERROR events exist          |

**Distributional Features**:

| Feature                    | Description                                            |
|---------------------------|--------------------------------------------------------|
| event_entropy             | Shannon entropy of the event type distribution         |
| n_unique_event_types      | Number of distinct event types observed                |
| n_unique_components       | Number of distinct source components                   |

**Note on Feature Exclusions**: The is_error feature is excluded from training (EXCLUDED_FEATURE_COLUMNS in isolation_forest.py) because it is a direct derivative of the error count and its inclusion would double-weight error information in the model.

### 5.3 Detection Module

The detection module implements the core anomaly detection pipeline using scikit-learn Isolation Forest algorithm.

#### 5.3.1 Isolation Forest Model

**Algorithm Overview**: Isolation Forest works on the principle that anomalous observations are "few and different" and can be isolated with fewer random partitions than normal observations. The algorithm builds an ensemble of isolation trees, where each tree recursively partitions the data by randomly selecting a feature and a split value. The path length required to isolate a point serves as the anomaly score: shorter paths indicate more anomalous points.

**Baseline Configuration**:
```python
IsolationForest(
    n_jobs=-1,           # Use all available CPU cores
    random_state=42      # Fixed seed for reproducibility
)
```

#### 5.3.2 Training Pipeline

The training pipeline performs the following steps:

1. Load Features: Read the extracted feature CSV
2. Load Labels: Read the anomaly label CSV
3. Merge: Inner-join features and labels on block_id
4. Extract Training Matrix: Select only TRAINING_FEATURE_COLUMNS
5. Fit Model: Train the Isolation Forest (unsupervised, labels not used during training)
6. Persist Model: Serialize the trained model using joblib

#### 5.3.3 Prediction Pipeline

The prediction pipeline generates predictions for each block:

1. Inference: Apply the trained model to generate raw predictions (-1 for anomaly, 1 for normal)
2. Score Computation: Compute anomaly scores using decision_function (negated so higher = more anomalous)
3. Label Mapping: Map raw predictions to human-readable labels
4. Output: Save predictions with block_id, true_label, predicted_label, and anomaly_score to CSV

#### 5.3.4 Evaluation Metrics

The evaluation module computes the following metrics:

| Metric         | Description                                                     |
|----------------|-----------------------------------------------------------------|
| Accuracy       | Overall proportion of correct predictions                       |
| Precision      | Proportion of predicted anomalies that are true anomalies       |
| Recall         | Proportion of true anomalies that are correctly detected        |
| F1 Score       | Harmonic mean of precision and recall                           |

All metrics treat "Anomaly" as the positive class, which is critical given the severe class imbalance (~2.9% anomaly rate). A model that predicts "Normal" for every block would achieve ~97.1% accuracy while detecting zero anomalies. F1 score on the anomaly class is therefore the primary optimization metric.

### 5.4 Optimization Module

The optimization module implements evolutionary optimization using Genetic Algorithms (GA) to jointly optimize feature selection and model hyperparameters.

#### 5.4.1 Genetic Algorithm Design

**Chromosome Encoding**: Each individual in the GA population is encoded as a chromosome with the following gene structure:

| Gene Index | Gene Name          | Type    | Range / Values                          |
|------------|--------------------|---------|-----------------------------------------|
| 0 to N-1   | feature__name      | Binary  | 0 or 1                                 |
| N          | n_estimators       | Integer | 50, 75, 100, 125, 150, 175, 200        |
| N+1        | max_samples        | Float   | 0.25 to 1.0                            |
| N+2        | max_features       | Float   | 0.5 to 1.0                             |
| N+3        | contamination      | Float   | 0.01 to 0.30                           |

Where N is the number of training feature columns. This encoding enables the GA to simultaneously explore which features contribute to detection quality and what hyperparameter values optimize the model.

**Fitness Function**: F1 score on the Anomaly class. F1 was chosen over accuracy because of the ~2.9% anomaly rate in the dataset.

**Stratified Subsampling**: To keep fitness evaluation tractable with 575,000+ blocks, the GA evaluates fitness on a fixed, label-stratified subsample.

**GA Configuration**:

| Parameter               | Value            |
|------------------------|------------------|
| Parent Selection       | Steady-State     |
| Crossover Type         | Single Point     |
| Mutation Type          | Random           |
| Mutation Rate          | 20% of genes     |
| Elitism               | 1                |

#### 5.4.2 Model Evolution System

The model evolution system manages the lifecycle of detection models:

**Version Promotion Logic**:
- If candidate F1 > current F1: Promote candidate to next version
- If candidate F1 <= current F1: Archive candidate with rejection timestamp

**Version History**: Every promotion or rejection decision is logged with full metadata.

### 5.6 Authentication and Security

The system uses JSON Web Tokens (JWT) for stateless authentication:

1. Registration: User provides email, name, and password (minimum 8 characters). Password is hashed using bcrypt. A JWT token is returned.
2. Login: User provides email and password. If valid, a JWT token is returned with 24-hour TTL.
3. Token Validation: Protected endpoints require Authorization: Bearer header.

**Key Security Design Decisions**:

- JWT secret is read per-call (not at import time) to avoid the module-import-before-dotenv issue
- CORS is configured to allow the Authorization header explicitly
- All errors return JSON to maintain CORS headers
- Debug mode defaults to off to prevent Werkzeug debugger exposure

- Accuracy is misleading: A trivial classifier predicting "Normal" for all blocks achieves ~97.1% accuracy
- F1 score is essential: Properly measures detection of the rare anomalous blocks
- Stratified evaluation is critical: Random sampling could produce evaluation sets with no anomalies

## 7. Experimental Results

### 7.1 Baseline Model Performance

The V1 baseline model is trained with default Isolation Forest parameters on the full training feature set (excluding is_error). Results are evaluated on the complete dataset and reported in data/evaluation/baseline_isolation_forest_metrics.json.

### 7.2 Genetic Algorithm Optimization

The GA optimization explores the joint feature-selection and hyperparameter space to find configurations that improve upon the baseline F1 score. For each GA run, the following are recorded:

- Best chromosome (feature mask + hyperparameters)
- Best fitness score (F1)
- Fitness progression per generation
- Per-generation wall clock times
- Total optimization wall clock time

### 7.3 Model Evolution and Versioning

The model evolution system ensures that only models demonstrating improvement are deployed:

- If candidate F1 > current F1: Promote to v(N+1)
- Otherwise: Archive candidate

Each decision is logged with full metadata enabling tracking of F1 improvement over model generations, identification of feature importance, analysis of hyperparameter convergence, and audit trail for security compliance.


## 9. Security Considerations

### 9.1 Authentication Security
- Passwords are hashed using bcrypt with automatic salting
- JWT tokens expire after 24 hours
- Unique email constraint prevents duplicate accounts
- Email format validation is performed server-side

### 9.2 API Security
- All pipeline and sources endpoints require valid JWT authentication
- CORS is configured to allow only the specified dashboard origin
- Error responses maintain CORS headers
- Debug mode is disabled by default

### 9.3 File Upload Security
- File extension allow-listing prevents dangerous file types
- 500MB size limit prevents denial-of-service
- Filenames are sanitized using secure_filename to prevent path traversal
- Timestamp-prefixed storage prevents filename collision

### 9.4 Database Security
- MongoDB connections use TLS with certificate verification
- Connection timeout of 15 seconds prevents indefinite blocking
- Environment-based configuration prevents credential hardcoding

### 9.5 Known Limitations
- JWT secret falls back to a default value if not configured
- No rate limiting on authentication endpoints
- File uploads stored on local filesystem (not suitable for horizontal scaling)
- Worker threads for upload processing have no retry mechanism

## 10. Limitations and Future Work

### 10.1 Current Limitations

1. **Batch Processing Only**: No real-time streaming ingestion
2. **Single Log Format for Detection**: Only HDFS logs in the detection pipeline
3. **Single Machine Deployment**: No distributed processing support
4. **No Autoencoder Integration**: Only Isolation Forest is implemented
5. **Cloud Connector Stubs**: AWS, Azure, GCP, Kafka, Syslog connectors are defined but not functional
6. **Limited Test Coverage**: Detection and optimization modules have limited tests

### 10.2 Proposed Future Enhancements

1. **Real-Time Streaming Pipeline**: Integrate Apache Kafka or Redis Streams
2. **Deep Learning Models**: LSTM-based and autoencoder-based detection
3. **Multi-Format Detection**: Anomaly detection across different log formats
4. **Distributed Processing**: Spark or Dask integration
5. **Alert Management**: Severity levels, deduplication, escalation policies
6. **Dashboard Integration**: Real-time anomaly visualization
7. **Multi-Tenancy**: Organization and project management
8. **Automated Retraining**: Scheduled model retraining and evolution
9. **Explainability**: Feature importance and anomaly explanation
10. **Benchmark Suite**: Compare against DeepLog, LogRobust, etc.

## 11. Conclusion

MorphGuard demonstrates a novel approach to cloud security log analytics that combines unsupervised anomaly detection with evolutionary optimization. By using Genetic Algorithms to jointly optimize feature selection and model hyperparameters, the system can continuously improve its detection capabilities without manual intervention.

Key contributions of this work include:

1. An end-to-end system from raw log ingestion through feature engineering, detection, optimization, and model evolution.
2. Application of Genetic Algorithms to simultaneously optimize feature selection and Isolation Forest hyperparameters, with proper handling of the contamination parameter.
3. A transparent versioning and promotion system that ensures only measurably superior models are deployed.
4. A secured REST API with JWT authentication, CORS handling, error management, and file upload capabilities.
5. A modular design with well-defined component boundaries that supports extension to new log formats, detection algorithms, and optimization strategies.
